# MyTracker Server

Бэкенд по функциональности `../../html+css+js`. React-фронтенд находится в `../Client` и подключён к API. Исходное автономное демо сохранено без изменений для сравнения. Запуск клиента: [Client/README.md](../Client/README.md).

Стек: Node.js 22.19+, TypeScript в strict-режиме, Express 5, PostgreSQL 17, `pg`, Zod, Helmet, Pino. Точные версии фиксируются в `package-lock.json`. Сервер не использует localStorage, JSON-файлы или in-memory базу для хранения пользовательских данных.

## Быстрый запуск с установленным PostgreSQL

Полная инструкция с командами создания PostgreSQL-базы и запуском двух терминалов находится в [корневом README](../../README.md#первый-запуск). Нужны Node.js 22.19+ и работающий PostgreSQL 17. Из корня проекта в PowerShell:

```powershell
cd .\TrackerWebApp\Server
npm ci
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Остальные команды этого README выполняются из `TrackerWebApp/Server`. Откройте `.env` и задайте подключение к своей базе:

```dotenv
NODE_ENV=development
HOST=127.0.0.1
PORT=3000
DATABASE_URL=postgresql://tracker:YOUR_DB_PASSWORD@127.0.0.1:5432/tracker
DATABASE_SSL=false
PUBLIC_URL=http://127.0.0.1:3000
FRONTEND_URL=http://127.0.0.1:5173
CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
ALLOW_DEMO_SEED=false
```

Замените `YOUR_DB_PASSWORD` своим паролем PostgreSQL. База `tracker` должна быть создана заранее и принадлежать пользователю `tracker`. При других реквизитах измените URL. Специальные символы пароля в URL нужно кодировать. `.env` исключён из Git; готовых рабочих реквизитов в репозитории нет. Примените миграции:

```powershell
npm run db:migrate
```

Для первого администратора задайте в `.env` собственные `ADMIN_EMAIL`, `ADMIN_PASSWORD` (12–128 символов), `ADMIN_DISPLAY_NAME` и выполните:

```powershell
npm run admin:create
```

После успешного создания очистите `ADMIN_PASSWORD` в `.env`. Если администратор уже существует, повторно создавать его не нужно. Такая инициализация новой базы оставляет одного администратора, без задач, очередей и других пользователей. Затем запустите API:

```powershell
npm run dev
```

API: [http://127.0.0.1:3000](http://127.0.0.1:3000). Проверка готовности: [GET /health/ready](http://127.0.0.1:3000/health/ready), успешный ответ — `{"status":"ok","database":"up"}`. Спецификация: [GET /api/openapi.json](http://127.0.0.1:3000/api/openapi.json) (OpenAPI 3.1, можно импортировать в Postman/Insomnia). Frontend запускается отдельно на порту 5173, см. [инструкцию клиента](../Client/README.md).

Остановка — `Ctrl+C`. При последующих запусках достаточно `npm run dev`; данные сохраняются в PostgreSQL. После обновления кода выполните `npm ci` и `npm run db:migrate` перед запуском. Изменения `.env` требуют перезапуска backend.

### Альтернатива для разработки: демо-администратор

Вместо `admin:create` можно установить `ALLOW_DEMO_SEED=true` в `.env` и выполнить:

```powershell
npm run db:seed
```

Обычный `npm run db:seed` переносит **только администратора** `admin@tracker.com` / `admin123` с полными правами (`isAdmin=true`). В исходном демо администратора «Мусаев Владимир Акмалович» нет, поэтому выбран `Admin`. Сотрудники, очереди, задачи и комментарии при обычном seed не создаются. Уже имеющиеся данные не удаляются, пароли и права существующих пользователей не меняются. Если email/ID занят другой учётной записью, seed останавливается без повышения её прав. Повторный seed не восстанавливает удалённого администратора и не сбрасывает его пароль.

Полный исходный снимок (6 пользователей, 3 очереди, 12 задач, 9 комментариев) сохранён в `seeds/demo.json` только для тестов и явной команды `npm run db:seed:full-demo`. Она требует отдельной пустой БД; после admin-only seed её нельзя применять в ту же базу. Оба варианта seed требуют `ALLOW_DEMO_SEED=true`, запрещены в production и не запускаются автоматически.

Демо-администратор: `admin@tracker.com` / `admin123` (также identifier `Admin`, пока имя не изменено). Только в полном тестовом снимке доступны `alice@example.com` / `pass123`, `bob@example.com` / `pass456`. Это публичные тестовые пароли, не для production. В БД записываются только scrypt-хеши.

Для production используйте `admin:create` со своим паролем. Команда создаёт нового администратора и не повышает права существующего пользователя.

## Очистка существующего трекера

Для однократной очистки используйте `DATABASE_URL` именно нужного трекера в `.env`. Команды из `Server`:

```powershell
npm run db:migrate
npm run db:reset
```

`db:reset` удаляет все очереди/доски, задачи, комментарии, журнал, внешние привязки входа и пользователей, кроме администратора. Его ID, имя, логин, пароль, права и текущие сессии сохраняются; тема меняется на тёмную, язык — на русский. Сессии удалённых пользователей отзываются каскадно. Операция выполняется целиком в транзакции. Если администраторов несколько, укажите `KEEP_ADMIN_ID` нужного; без однозначного выбора или при отсутствии у администратора пароля команда останавливается до удаления данных. Повторная очистка допустима, но также удалит всё, созданное после первой.

Очистка не запускается при старте приложения, миграциях или seed. История seed сохраняется, поэтому прежний полный демо-снимок не восстанавливается. Обычная инициализация новой базы создаёт только администратора и оставляет пул пустым.

При нескольких администраторах задайте `KEEP_ADMIN_ID` в `.env` или окружении терминала перед `db:reset`. Это ID из `GET /api/users`, а не имя или email. После выполнения уберите эту настройку и обновите страницу трекера.

## Сборка и запуск без watch

С ранее настроенным `.env` и применёнными миграциями:

```powershell
npm run build
npm start
```

Остановите прежний процесс API перед запуском, чтобы освободить порт 3000. Backend раздаёт frontend с того же адреса, если предварительно выполнен `npm run build` в `Client` и существует `Client/dist`. Иначе он обслуживает только API; используйте отдельный Vite либо соберите клиент. Полная последовательность сборки обоих проектов — в [корневом README](../../README.md#запуск-собранной-версии).

В production обязательны `NODE_ENV=production`, HTTPS в `PUBLIC_URL` и `FRONTEND_URL`, защищённое подключение к БД (`DATABASE_SSL=true` для удалённого TLS-сервера), сильные пароли и узкий список `CORS_ORIGINS`. TLS завершает ваш reverse proxy; сам Express слушает HTTP. `TRUST_PROXY_HOPS` меняйте только под известную топологию прокси. Не открывайте PostgreSQL в интернет.

## Docker Compose (альтернатива)

Docker не обязателен. Если он установлен, в `.env` задайте `POSTGRES_PASSWORD` и выполните:

```powershell
docker compose up --build -d
docker compose run --rm -e ALLOW_DEMO_SEED=true api node dist/db/cli.js seed
```

Сервис `migrate` применяет миграции до запуска API. Compose по умолчанию работает в development; для production используйте свой HTTPS URL, `NODE_ENV=production` и не запускайте seed. База опубликована только на `127.0.0.1:5433` (настраивается через `POSTGRES_PORT`), API — на `127.0.0.1:3000`. Внутри Compose URL БД собирается из `POSTGRES_*`; для локального Node нужен отдельный `DATABASE_URL`. Для простоты используйте длинный случайный буквенно-цифровой пароль, иначе URL-кодируйте специальные символы.

Данные находятся в именованном томе `tracker_data`. `docker compose down` сохраняет его; не добавляйте `-v`, если не хотите удалить данные. Docker-конфигурация приложена, но основной интеграционный прогон выполняется на локальном PostgreSQL, не в Docker.

## Авторизация и формат API

```http
POST /api/auth/login
Content-Type: application/json

{"identifier":"admin@tracker.com","password":"admin123"}
```

Ответ: `{ "data": { "user": {...}, "accessToken": "...", "tokenType": "Bearer", "expiresAt": "..." } }`.

Вход принимает email или отображаемое имя без учёта регистра, как в демо (включая кириллицу). Email имеет приоритет. Одинаковые имена разрешены, но при таком входе сервер возвращает `400 LOGIN_EMAIL_REQUIRED` и просит email; он уникален без учёта регистра и пробелов по краям. После переименования вход по имени использует новое имя, отдельного постоянного алиаса `admin` нет. Публичный `POST /api/auth/register` возвращает `403 REGISTRATION_DISABLED`. Только администратор создаёт сотрудника через `POST /api/users` с `{displayName,email,password}` (8–128 символов) и самостоятельно передаёт реквизиты. Ответ содержит только пользователя, без новой сессии и без пароля; `isAdmin` задавать нельзя.

Для API-клиентов сохранён `Authorization: Bearer <accessToken>`. React отправляет `X-Tracker-Browser: 1`: при login сервер устанавливает cookie `tracker_session` (`HttpOnly`, `SameSite=Lax`, `Path=/api`, `Secure` в production) и возвращает `{user,expiresAt}` без токена. Все запросы React используют `credentials: include`. Изменения с cookie требуют заголовок `X-Tracker-Browser: 1`; Origin проверяется по `PUBLIC_URL`, `FRONTEND_URL` и `CORS_ORIGINS`. Пароли/хеши никогда не возвращаются. Случайные 256-битные токены действуют 7 дней по умолчанию; в БД хранится SHA-256 токена. Logout удаляет сессию и cookie, logout-all отзывает все сессии пользователя. После истечения срока нужен новый вход. localStorage/sessionStorage для токенов не используется.

POST/PATCH требуют `Content-Type: application/json`, включая logout с телом `{}`. Ответы — `{data: ...}`, списки задач/пользователей дополнены `pagination: {total,limit,offset}`. По умолчанию 50 записей, максимум 100. Пустые ответы удаления — HTTP 204; удаление очереди возвращает очередь и число удалённых задач.

Ошибки: `{error: {code,message,details?,requestId}}`. Коды: 400 — некорректные данные, 401 — нет действующей сессии, 403 — недостаточно прав или отключённый способ входа, 404 — не найдено, 409 — конфликт, 413 — большое тело, 415 — не JSON, 429 — лимит запросов, 503 — БД не готова. Пароли, тела, заголовки Authorization и query string не попадают в HTTP-логи.

## Возможности и соответствие демо

| Область | Маршруты |
| --- | --- |
| Вход, текущий пользователь, выход | `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`, `POST /api/auth/logout-all` |
| Пользователи, создание администратором, имена/роли | `GET/POST /api/users`, `GET/PATCH /api/users/:id` |
| Очереди | `GET/POST /api/queues`, `GET/DELETE /api/queues/:id`, `GET /api/queues/by-key/:key` |
| Задачи | `GET/POST /api/issues`, `GET/PATCH/DELETE /api/issues/:id`, `GET /api/issues/by-key/:key` |
| Комментарии | `GET/POST /api/issues/:id/comments`, `DELETE /api/issues/:id/comments/:commentId` |
| Статистика и справочники | `GET /api/issues/stats`, `GET /api/metadata` |
| Журнал и настройки | `GET /api/activity`, `GET/PATCH /api/settings` |

Модель доступа — **одно общее рабочее пространство**, как в демо, без организаций и приватных очередей. Каждый авторизованный пользователь видит пользователей/задачи, создаёт очереди и задачи, редактирует и удаляет задачи. Только администратор меняет имена/роли и удаляет очереди. Комментарий удаляет только автор (включая ограничение для администратора, как в интерфейсе демо).

`role` — должность/отображаемая роль, допускающая свой текст и русские алиасы. Она **не управляет** `isAdmin`; назвать сотрудника `Administrator` недостаточно для повышения прав. Через API нельзя передать `isAdmin`, `reporterId`, `authorId`, ID, счётчик или серверные даты.

Цвет нового пользователя выбирается из палитры демо по числу уже существующих пользователей; одновременные создания администратором получают последовательные позиции. Цвета уже существующих пользователей не перезаписываются.

Ключ новой очереди — от 1 до 10 латинских букв (`A` допустим); регистр приводится к верхнему. Цифры и подчёркивания, отсутствующие в правилах формы демо, не принимаются. Перед запуском обновлённого сервера выполните `npm run db:migrate`: миграция `002_demo_queue_keys.sql` обновляет ограничение PostgreSQL, не меняя исходную миграцию. Старые очереди с ключами прежнего формата сохраняются без переименования и остаются доступны для чтения, создания задач и удаления.

Фильтры задач: `queueId`, `status`, `priority`, `type`, `assigneeId`, `myTasks=true`, `search`, `limit`, `offset`. Множественные значения: `?status=Open&status=Done&priority=High`. Поиск без учёта регистра по заголовку, описанию и ключу, `%`/`_` трактуются буквально. Сортировка: `updatedAt DESC, id`. `/api/issues/stats` принимает те же фильтры, но считает весь набор, независимо от страницы.

Статусы: `Open`, `In Progress`, `Need Info`, `Done`, `Closed`; приоритеты: `High`, `Medium`, `Low`; типы: `Task`, `Bug`, `Story`, `Epic`. В работающем демо любые статусы выбираются напрямую — это сохранено. `metadata.transitions` повторяет таблицу рекомендованных переходов, но не ограничивает PATCH. `statusChangedAt` обновляется только при реальной смене статуса, не при редактировании текста/комментария; клиент сможет вычислять таймер по этому полю.

Нумерация задач атомарна в рамках очереди. Удалённые номера не переиспользуются. PATCH принимает необязательную `version` из последнего GET: если задача уже изменена другим запросом, возвращается `409 VERSION_CONFLICT`. Без version действует совместимое с демо поведение последней записи. Пропущенные поля PATCH не сбрасываются. Удаление очереди каскадно удаляет задачи и комментарии в транзакции; журнал остаётся. История теперь сохраняется целиком, `/api/activity` по умолчанию отдаёт последние 20 записей.

Тема и язык (`light/dark`, `en/ru`) сохраняются для каждого пользователя и подключены к React. По умолчанию используются **тёмная тема и русский язык**: на экране входа и для новых пользователей. Миграция `003_default_preferences.sql` меняет SQL defaults, сохраняя ранее выбранные настройки существующих пользователей; `db:reset` устанавливает новые значения и оставляемому администратору. Клиентские анимации, drag-and-drop и отрисовка перенесены в `Client`. Данные из localStorage исходного демо автоматически не импортируются.

## Только логин и пароль

Вход через Google, Яндекс, Mail и другие внешние сайты отключён полностью. Кнопки, серверный обмен кодов и настройки провайдеров удалены. Для старых клиентов `GET /api/auth/providers` возвращает пустой список, любые запросы под `/api/auth/oauth` — `403 EXTERNAL_AUTH_DISABLED`, включая callback. Ранее настроенные ключи провайдеров не включают вход. Существующие таблицы внешних привязок оставлены для совместимости миграций; `db:reset` очищает их.

## Проверка

```powershell
npm run typecheck
npm test
npm run build
```

Или `npm run check` для всех трёх шагов. Интеграционные тесты отправляют настоящие HTTP-запросы к Express и выполняют SQL в настоящем PostgreSQL. Мок БД не используется.

По умолчанию тестовый помощник ищет `initdb`/`pg_ctl` в `PG_BIN`, стандартном каталоге PostgreSQL 17 на Windows или PATH. Создаёт отдельный временный кластер с случайным паролем, SCRAM и loopback-интерфейсом; после тестов останавливает его и удаляет только свой временный каталог. Не запускайте initdb от root на Unix.

Альтернатива — задать `TEST_DATABASE_URL` отдельной тестовой БД. В ней создаётся уникальная схема `tracker_test_<random>`, только она удаляется после тестов. `DATABASE_URL` вашей разработки для тестов не используется. У тестового пользователя должно быть право CREATE SCHEMA. Отсутствие доступного PostgreSQL считается ошибкой, тесты не пропускаются молча.

Проверяются seed/миграции, все основные API-операции, роли/ownership, отсутствие паролей в ответах, сессии, настройки по умолчанию, фильтры, каскады, откат транзакций, 16 параллельных созданий, конфликт version, таймеры, SQL-инъекции, валидация, CORS, лимиты, блокировка внешнего входа, очистка с сохранением администратора и сохранение данных между экземплярами API.

### Postman / Insomnia

Импортируйте `docs/MyTracker.postman_collection.json`, задайте `baseUrl`, запустите сервер с **отдельной тестовой БД**, заполненной `npm run db:seed:full-demo`, затем выполните коллекцию по порядку. Обычный admin-only seed для этой коллекции недостаточен: она использует Alice. Коллекция получает токены, создаёт тестовую очередь/задачу/комментарий, проверяет ответы и удаляет созданную очередь. Исходные демо-задачи не удаляются. Секреты коллекция не содержит; публичные demo-пароли используются только для локальной проверки. Альтернатива — импортировать `/api/openapi.json`.

## Эксплуатационные границы

- Это backend для единого пространства демо, не multi-tenant SaaS. Подтверждение email, восстановление пароля, приглашения и отдельные организации в демо отсутствовали и здесь не добавлены.
- Лимитер запросов хранит счётчики в памяти процесса: 600 API-запросов/минуту и 30 auth-запросов/15 минут на IP. Перед запуском нескольких реплик нужен общий store/лимитирование на доверенном proxy.
- Миграции последовательные, в транзакции, с advisory lock и checksum. Автоматического разрушительного rollback нет; изменения схемы делайте новой миграцией и перед production обновлением создавайте backup.
- Идентификаторы объектов и связи соответствуют демо; новые объекты получают UUID. Истёкшие сессии/OAuth state удаляются сервером каждый час.
- Текущая ветка не коммитится и не публикуется автоматически.
