# MyTracker Server

Бэкенд по функциональности `../../html+css+js`. Исходный фронтенд не изменён и пока не подключён к API. `../Client` оставлен пустым.

Стек: Node.js 22.19+, TypeScript в strict-режиме, Express 5, PostgreSQL 17, `pg`, Zod, Helmet, Pino. Точные версии фиксируются в `package-lock.json`. Сервер не использует localStorage, JSON-файлы или in-memory базу для хранения пользовательских данных.

## Быстрый запуск с установленным PostgreSQL

Все команды ниже выполняются из `TrackerWebApp/Server`.

1. Создайте **отдельную** PostgreSQL-базу `tracker` и пользователя с правами на неё. Не используйте чужую рабочую базу. Пароль задайте самостоятельно.
2. Скопируйте `.env.example` в `.env`; укажите реальный `DATABASE_URL` и остальные настройки. `.env` исключён из Git.
3. Выполните:

```powershell
npm ci
npm run db:migrate
```

Для разработки с исходными демо-данными установите `ALLOW_DEMO_SEED=true` в `.env`, затем:

```powershell
npm run db:seed
npm run dev
```

API: `http://localhost:3000`. Проверка готовности: `GET /health/ready`. Спецификация: `GET /api/openapi.json` (OpenAPI 3.1, можно импортировать в Postman/Insomnia).

Seed переносит 6 пользователей, 3 очереди, 12 задач и 9 комментариев из демо с сохранением ID, текстов и связей. Снимок лежит в `seeds/demo.json`; он не зависит от расположения фронтенда. Seed не запускается автоматически, запрещён в production, отказывается смешиваться с уже заполненной базой и при повторном запуске не восстанавливает удалённые данные/не сбрасывает пароли.

Демо-учётные записи: `admin@tracker.com` / `admin123` (также identifier `admin`), `alice@example.com` / `pass123`, `bob@example.com` / `pass456`. Это публичные тестовые пароли, не для production. В БД записываются только scrypt-хеши.

Для пустой production-базы вместо seed задайте `ADMIN_EMAIL`, `ADMIN_PASSWORD` (минимум 12 символов), `ADMIN_DISPLAY_NAME` и выполните `npm run admin:create`. Команда создаёт нового администратора и не повышает права существующего пользователя. После создания уберите пароль из окружения.

Сборка и запуск без watch:

```powershell
npm run build
npm start
```

В production обязательны HTTPS в `PUBLIC_URL`, защищённое подключение к БД (`DATABASE_SSL=true` для удалённого TLS-сервера), сильные пароли и узкий список `CORS_ORIGINS`. TLS завершает ваш reverse proxy; сам Express слушает HTTP. `TRUST_PROXY_HOPS` меняйте только под известную топологию прокси. Не открывайте PostgreSQL в интернет.

## Docker Compose (альтернатива)

Docker не обязателен. Если он установлен, в `.env` задайте `POSTGRES_PASSWORD` и выполните:

```powershell
docker compose up --build -d
docker compose run --rm -e ALLOW_DEMO_SEED=true api node dist/db/cli.js seed
```

Сервис `migrate` применяет миграции до запуска API. Compose по умолчанию работает в development; для production используйте свой HTTPS URL, `NODE_ENV=production` и не запускайте seed. База опубликована только на `127.0.0.1:5433` (настраивается через `POSTGRES_PORT`), API — на `127.0.0.1:3000`. Внутри Compose URL БД собирается из `POSTGRES_*`; для локального Node нужен отдельный `DATABASE_URL`. Для простоты используйте длинный случайный буквенно-цифровой пароль, иначе URL-кодируйте специальные символы.

Данные находятся в именованном томе `tracker_data`. `docker compose down` сохраняет его; не добавляйте `-v`, если не хотите удалить данные. Docker-конфигурация приложена, но основной интеграционный прогон выполняется на локальном PostgreSQL, не в Docker.

## Авторизация и формат API

```http
POST /api/auth/login
Content-Type: application/json

{"identifier":"alice@example.com","password":"pass123"}
```

Ответ: `{ "data": { "user": {...}, "accessToken": "...", "tokenType": "Bearer", "expiresAt": "..." } }`.

Для защищённых запросов передавайте `Authorization: Bearer <accessToken>`. Пароли/хеши никогда не возвращаются. Случайные 256-битные токены действуют 7 дней по умолчанию; в БД хранится SHA-256 токена. Logout удаляет сессию немедленно, logout-all отзывает все сессии пользователя. Автоматического обновления токенов нет: после истечения срока нужен новый вход. При подключении браузерного клиента не храните bearer-токен в localStorage; спроектируйте безопасное хранение/сессионный BFF.

POST/PATCH требуют `Content-Type: application/json`, включая logout с телом `{}`. Ответы — `{data: ...}`, списки задач/пользователей дополнены `pagination: {total,limit,offset}`. По умолчанию 50 записей, максимум 100. Пустые ответы удаления — HTTP 204; удаление очереди возвращает очередь и число удалённых задач.

Ошибки: `{error: {code,message,details?,requestId}}`. Коды: 400 — некорректные данные, 401 — нет действующей сессии, 403 — недостаточно прав, 404 — не найдено, 409 — конфликт, 413 — большое тело, 415 — не JSON, 429 — лимит запросов, 503 — OAuth не настроен/БД не готова. Пароли, тела, заголовки Authorization, коды OAuth и query string не попадают в HTTP-логи.

## Возможности и соответствие демо

| Область | Маршруты |
| --- | --- |
| Регистрация, вход, текущий пользователь, выход | `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`, `POST /api/auth/logout-all` |
| Пользователи, администрирование имён/ролей | `GET /api/users`, `GET/PATCH /api/users/:id` |
| Очереди | `GET/POST /api/queues`, `GET/DELETE /api/queues/:id`, `GET /api/queues/by-key/:key` |
| Задачи | `GET/POST /api/issues`, `GET/PATCH/DELETE /api/issues/:id`, `GET /api/issues/by-key/:key` |
| Комментарии | `GET/POST /api/issues/:id/comments`, `DELETE /api/issues/:id/comments/:commentId` |
| Статистика и справочники | `GET /api/issues/stats`, `GET /api/metadata` |
| Журнал и настройки | `GET /api/activity`, `GET/PATCH /api/settings` |
| OAuth | `GET /api/auth/providers`, `GET /api/auth/oauth/:provider`, `GET /api/auth/oauth/:provider/callback` |

Модель доступа — **одно общее рабочее пространство**, как в демо, без организаций и приватных очередей. Каждый авторизованный пользователь видит пользователей/задачи, создаёт очереди и задачи, редактирует и удаляет задачи. Только администратор меняет имена/роли и удаляет очереди. Комментарий удаляет только автор (включая ограничение для администратора, как в интерфейсе демо).

`role` — должность/отображаемая роль, допускающая свой текст и русские алиасы. Она **не управляет** `isAdmin`; назвать сотрудника `Administrator` недостаточно для повышения прав. Через API нельзя передать `isAdmin`, `reporterId`, `authorId`, ID, счётчик или серверные даты.

Фильтры задач: `queueId`, `status`, `priority`, `type`, `assigneeId`, `myTasks=true`, `search`, `limit`, `offset`. Множественные значения: `?status=Open&status=Done&priority=High`. Поиск без учёта регистра по заголовку, описанию и ключу, `%`/`_` трактуются буквально. Сортировка: `updatedAt DESC, id`. `/api/issues/stats` принимает те же фильтры, но считает весь набор, независимо от страницы.

Статусы: `Open`, `In Progress`, `Need Info`, `Done`, `Closed`; приоритеты: `High`, `Medium`, `Low`; типы: `Task`, `Bug`, `Story`, `Epic`. В работающем демо любые статусы выбираются напрямую — это сохранено. `metadata.transitions` повторяет таблицу рекомендованных переходов, но не ограничивает PATCH. `statusChangedAt` обновляется только при реальной смене статуса, не при редактировании текста/комментария; клиент сможет вычислять таймер по этому полю.

Нумерация задач атомарна в рамках очереди. Удалённые номера не переиспользуются. PATCH принимает необязательную `version` из последнего GET: если задача уже изменена другим запросом, возвращается `409 VERSION_CONFLICT`. Без version действует совместимое с демо поведение последней записи. Пропущенные поля PATCH не сбрасываются. Удаление очереди каскадно удаляет задачи и комментарии в транзакции; журнал остаётся. История теперь сохраняется целиком, `/api/activity` по умолчанию отдаёт последние 20 записей.

Тема и язык (`light/dark`, `en/ru`) сохраняются для каждого пользователя. Клиентские анимации, drag-and-drop и отрисовка остаются задачей будущего фронтенда. Данные, уже изменённые в localStorage конкретного браузера, автоматически не импортируются: seed содержит исходный снимок демо.

## Google, Яндекс, Mail

В демо кнопки имитировали вход без проверки личности. Здесь нет эндпоинта, позволяющего войти по присланному email провайдера. Реализован серверный authorization-code flow для `google`, `yandex`, `mail`.

1. Зарегистрируйте OAuth-приложение у нужного провайдера.
2. Укажите redirect URI точно: `<PUBLIC_URL>/api/auth/oauth/google/callback` (аналогично `yandex`, `mail`).
3. Запишите `<PROVIDER>_CLIENT_ID` и `<PROVIDER>_CLIENT_SECRET` в локальное окружение/менеджер секретов. Не коммитьте их и не передавайте в переписке.
4. Откройте `GET /api/auth/oauth/google` в браузере. Callback возвращает JSON с сессией — это backend-only контракт до подключения фронтенда, без перенаправления токенов в URL.

Используются одноразовый state с TTL 10 минут, привязка к HttpOnly SameSite=Lax cookie, PKCE S256 для Google/Яндекса, HTTPS-запросы с таймаутом, проверка идентификатора профиля. Для Google требуется `email_verified=true`. Учётные записи не склеиваются автоматически по совпадению email: возвращается `409 ACCOUNT_LINK_REQUIRED`, нужно войти исходным способом. UI привязки аккаунтов в этом этапе не реализован.

Без credentials провайдер отключён и отвечает `503 OAUTH_NOT_CONFIGURED`. Тесты проверяют обмен кода и защиту на контролируемом HTTP-адаптере провайдера; **реальный вход в аккаунты Google/Яндекс/Mail без ваших зарегистрированных приложений не проверялся**.

Использованные источники: [Express 5](https://expressjs.com/en/guide/migrating-5/), [транзакции node-postgres](https://node-postgres.com/features/transactions), [Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Яндекс OAuth/PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url), [Mail: официальная справка](https://help.mail.ru/developers/oauth/), [Mail endpoints в Auth.js](https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/providers/mailru.ts).

## Проверка

```powershell
npm run typecheck
npm test
npm run build
```

Или `npm run check` для всех трёх шагов. Интеграционные тесты отправляют настоящие HTTP-запросы к Express и выполняют SQL в настоящем PostgreSQL. Мок БД не используется.

По умолчанию тестовый помощник ищет `initdb`/`pg_ctl` в `PG_BIN`, стандартном каталоге PostgreSQL 17 на Windows или PATH. Создаёт отдельный временный кластер с случайным паролем, SCRAM и loopback-интерфейсом; после тестов останавливает его и удаляет только свой временный каталог. Не запускайте initdb от root на Unix.

Альтернатива — задать `TEST_DATABASE_URL` отдельной тестовой БД. В ней создаётся уникальная схема `tracker_test_<random>`, только она удаляется после тестов. `DATABASE_URL` вашей разработки для тестов не используется. У тестового пользователя должно быть право CREATE SCHEMA. Отсутствие доступного PostgreSQL считается ошибкой, тесты не пропускаются молча.

Проверяются seed/миграции, все основные API-операции, роли/ownership, отсутствие паролей в ответах, сессии, настройки, фильтры, каскады, откат транзакций, 16 параллельных созданий, конфликт version, таймеры, SQL-инъекции, валидация, CORS, лимиты, OAuth state/PKCE/replay и сохранение данных между экземплярами API.

### Postman / Insomnia

Импортируйте `docs/MyTracker.postman_collection.json`, задайте `baseUrl`, запустите сервер с demo seed, затем выполните коллекцию по порядку. Она получает токены, создаёт тестовую очередь/задачу/комментарий, проверяет ответы и удаляет созданную очередь. Исходные демо-задачи не удаляются. Секреты коллекция не содержит; публичные demo-пароли используются только для локальной проверки. Альтернатива — импортировать `/api/openapi.json`.

## Эксплуатационные границы

- Это backend для единого пространства демо, не multi-tenant SaaS. Подтверждение email, восстановление пароля, приглашения и отдельные организации в демо отсутствовали и здесь не добавлены.
- Лимитер запросов хранит счётчики в памяти процесса: 600 API-запросов/минуту и 30 auth-запросов/15 минут на IP. Перед запуском нескольких реплик нужен общий store/лимитирование на доверенном proxy.
- Миграции последовательные, в транзакции, с advisory lock и checksum. Автоматического разрушительного rollback нет; изменения схемы делайте новой миграцией и перед production обновлением создавайте backup.
- Идентификаторы объектов и связи соответствуют демо; новые объекты получают UUID. Истёкшие сессии/OAuth state удаляются сервером каждый час.
- Текущая ветка не коммитится и не публикуется автоматически.
